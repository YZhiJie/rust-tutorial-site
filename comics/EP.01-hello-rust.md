# EP.01 第一行 Rust 代码

> 对应正文：[guide/01-hello-rust.md](../docs/guide/01-hello-rust.md)（Hello, Rust / 编译与运行 / println! 的格式化 / 一个稍完整的例子）

## 剧情回顾

- **第 1 格**：齿轮君兴冲冲写下第一行打印，却收到 `error[E0425]: cannot find function println`——他漏掉了 `!`。`println!` 是宏，不是函数。
- **第 2 格**：码叔拆解流水线：`main.rs` 经 rustc 编译成机器码才执行；`cargo run` 只是把"编译 + 运行"合成一条命令，产物落在 `target/` 目录。
- **第 3 格**：像素酱发现 `f64 * i32` 直接报错——Rust 不做隐式数值转换，必须 `as` 显式转换。
- **第 4 格**：码叔结案——Rust 的严格全部发生在编译期，越早报错，线上越少救火。

## 知识点拆解

### 第 1 格 · 宏与那个感叹号

- `println!` 末尾的 `!` 是**宏调用**的标记。宏在编译期展开成普通代码，因此能接受可变参数并在编译期检查格式串；
- 写成 `println(...)` 时，编译器按"函数"去解析，自然找不到——`error[E0425]` 的含义就是"这个名字在当前作用域不存在"；
- 同类宏还有 `format!`、`vec!`、`panic!`、`assert_eq!`，都带 `!`。

### 第 2 格 · AOT 编译与 Cargo

Rust 是提前编译（AOT）语言：

1. `rustc main.rs` 直接编译单文件，得到可执行文件；
2. 真实项目用 Cargo：`cargo new` 生成 `Cargo.toml + src/main.rs`，`cargo run` 编译并运行，`cargo build --release` 产出优化后的二进制；
3. `cargo run` 不是解释执行——它只是把"编译 + 运行"合并，每次都会先做增量编译。

宏展开也发生在编译阶段：`println!("{:.2}", x)` 会在编译期核对占位符数量与参数类型，不匹配直接编译失败，而不是运行时才炸。

### 第 3 格 · 没有隐式转换

```rust
let price = 29.9;   // f64
let count = 3;      // i32
price * count       // error[E0277]：类型不匹配
price * count as f64 // ✓ 显式转换后通过
```

- 不同类型之间不会"自动看齐"，`i32` 与 `f64` 相乘必须显式 `as`；
- 换来的是可预测性：精度丢失、截断、溢出都由开发者显式选择，不会悄悄发生；
- `as` 只是手段之一，更稳妥的转换见 `From`/`Into`（教程第 08 章错误处理会再遇到）。

### 第 4 格 · 编译期严格是礼物

- `println` 漏 `!`、类型混算、格式串占位符不匹配——这些在别的语言里可能拖到运行时才暴露；
- Rust 把它们全部前置到编译期，配合"错误码 + help 建议"，照着改就能过；
- 读懂错误码是基本功：E0425 找不到名字、E0277 类型/trait 不满足，附录《常见错误速查》有一份对照表。

## 坑点清单

> 🔗 正文对照：[《附录 · 常见错误速查》](../docs/appendix/errors.md)

1. `println` 漏写 `!` → `error[E0425]`，所有带 `!` 的宏同理；
2. `f64` 与 `i32` 直接混算 → `error[E0277]`，先 `as` 或用 `f64::from`；
3. 把 `cargo run` 当成解释执行，忽略 `target/` 里的真实产物与 release 优化的差异。

## 自测 3 题（含答案）

1. `println!` 的 `!` 代表什么？——**宏调用标记；宏在编译期展开，因此能检查格式串与参数**。
2. `cargo run` 是解释执行吗？——**不是，它先做增量编译再运行产物，二进制在 `target/debug/` 下**。
3. 为什么 `29.9 * 3` 在 Rust 里直接报错？——**Rust 不做隐式数值转换，`f64` 与 `i32` 必须用 `as` 显式转换后才能运算**。
