# EP.12 宏与 unsafe 边界

> 对应正文：[guide/12-macros-unsafe.md](../docs/guide/12-macros-unsafe.md)（宏能解决什么问题 / macro_rules! 与重复 / 卫生性 / unsafe 与安全契约 / extern "C" 与 FFI）

## 剧情回顾

- **第 1 格**：齿轮君想手写一个"可变参数的打印函数"，发现普通函数的签名必须把参数个数与类型写死——可变参数只能上宏。
- **第 2 格**：码叔揭秘 `macro_rules!`：按模式匹配展开，`$( ... ),*` 做逗号分隔的重复捕获；`vec!`/`println!` 都是同款原理；宏有卫生性，不会意外捕获调用点变量。
- **第 3 格**：像素酱实证 unsafe：解引用裸指针必须放进 `unsafe { }` 块；这不是关闭检查，而是向编译器担保安全契约；`extern "C"` 的 FFI 调用同样走 unsafe。
- **第 4 格**：码叔结案：宏在编译期展开，unsafe 在边界立约；两者都要克制。

## 知识点拆解

### 第 1 格 · 函数做不到的事

- 函数要求参数的类型与数量在调用点已经确定；
- `println!` 接受可变数量的参数并做格式检查，`vec!` 接受任意数量的元素，`derive` 自动生成 trait 实现——这些都由宏在编译期生成代码；
- Rust 的宏分两类：声明宏（`macro_rules!`，按语法模式匹配展开）与过程宏（派生、属性、函数式三类，处理 token 流）；宏展开发生在编译期，运行时没有额外调用开销，但错误定位比普通函数困难。

### 第 2 格 · macro_rules! 与卫生性

- 每条规则左边是匹配模式，右边是展开结果；`$name:片段类型` 捕获语法片段，常见类型有 `expr`、`ident`、`ty`、`pat`、`tt`；
- `$(...)*` 重复匹配零次或多次，`$(...),*` 以逗号分隔，`$(,)?` 允许末尾多余逗号；捕获的 `$x` 必须出现在 `$(...)*` 内部，否则报 `variable 'x' is still repeating at this depth`；
- 卫生性（hygiene）让宏内部的标识符与调用点标识符处于不同语法上下文，互不遮蔽；跨 crate 导出宏时内部路径应使用 `$crate`。

```rust
macro_rules! sum {
    ($($x:expr),* $(,)?) => {{
        let mut total = 0;
        $(total += $x;)*
        total
    }};
}

fn main() {
    println!("{}", sum!(1, 2, 3, 4));
    println!("{}", sum!()); // 命中零次重复
}
```

### 第 3 格 · unsafe 是契约不是开关

- `unsafe` 不关闭借用检查、类型检查与生命周期检查，只是额外允许五类操作：解引用裸指针、调用 `unsafe fn`、访问或修改可变静态变量、实现 `unsafe trait`、访问联合体字段；
- 创建裸指针本身是安全操作，解引用才需要 `unsafe`；调用 `unsafe fn` 漏写块会报 `error[E0133]`；
- 用 `unsafe` 等于向编译器承诺前置条件成立（安全契约），违反契约就是未定义行为；自定义 `unsafe fn` 应在文档注释写明 `# Safety` 要求；
- FFI 边界用 `extern "C"` 声明签名、在 `unsafe` 块中调用；跨边界只传 FFI 安全的类型：整数、浮点数、裸指针、`#[repr(C)]` 结构体，`String`/`Vec` 的布局不受保证。

```rust
unsafe fn read_raw(ptr: *const i32) -> i32 {
    unsafe { *ptr }
}

extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    let value = unsafe { abs(-42) };
    println!("{value}");
}
```

### 第 4 格 · 边界守则

- `unsafe` 块越小越好，只把需要担保契约的那几行放进去，说不清契约时应优先重构为安全抽象；
- 别名与生命周期契约一旦违反即 UB，编译器不再保证程序语义；
- 跨 FFI 传字符串与内存时，必须约定由哪一侧释放；C 字符串借助 `std::ffi::CStr`、`CString` 转换。

## 坑点清单

1. 把大段代码随手包进 `unsafe` → 契约说不清、审查无从下手，尽量压缩到最小范围；
2. `unsafe` 里违反别名或生命周期契约 → 未定义行为（UB），后果比 panic 严重得多；
3. FFI 字符串与内存归属没约定清楚 → 泄漏或悬垂指针，先写明由哪一侧释放。

## 自测 3 题（含答案）

1. 宏的卫生性解决什么问题？——**让宏内部引入的标识符与调用点标识符处于不同语法上下文，防止宏意外遮蔽或捕获调用方的同名变量**。
2. `unsafe` 是"关闭安全检查"的开关吗？——**不是，借用、类型与生命周期检查照常执行，它只是额外解锁五类操作，安全契约由开发者向编译器担保**。
3. 哪些类型可以安全穿过 FFI 边界？——**整数、浮点数、裸指针与 `#[repr(C)]` 结构体；`String`、`Vec` 等应传指针加长度，并明确由哪一侧释放**。
